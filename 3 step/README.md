# Этап 3: пошаговая СМО, вариант 6 (Java, консоль)

**Цель:** отладочная демонстрация дискретно-событийной модели. **Без GUI, без Maven/Gradle, без внешних библиотек.** Программа сама генерирует заявки по заданным законам, а пользователь нажатием Enter разрешает выполнение следующего события. При необходимости ход моделирования сохраняется в UTF-8 TXT.

## 1. Соответствие варианту 6

**ИБ – ИЗ2 – ПЗ1 – Д1ОЗ2 – Д1ОО2 – Д2П2 – Д2Б5 – ОР1 – ОД3** (таблица вариантов и приложение 3 методички).

| Код | Реализация |
| --- | --- |
| ИБ | Неограниченное число заявок от каждого источника; лимит `--requests` останавливает **эксперимент**, а не изменяет тип источников. |
| ИЗ2 | Интервал между генерациями `U(a, b)` для каждого источника. |
| ПЗ1 | Продолжительность обслуживания `-mean * ln(1-U)`. |
| Д1ОЗ2 | Общий буфер `List<Request>`: постановка в конец, после удаления элементы сдвигаются к началу. Указатель постановки **не нужен**. |
| Д1ОО2 | При заполненном буфере выбивается заявка **внутри буфера** от источника с наименьшим приоритетом. При равенстве — самая старая (как на вашей диаграмме). Новая заявка ставится в конец. |
| Д2П2 | Кольцевой поиск **свободного** прибора, начиная от указателя. После назначения указатель передвигается на следующий. Занятый прибор не отказывает заявке. |
| Д2Б5 | При возникновении триггера и отсутствии активного пакета выбирается наиболее приоритетный источник в буфере. Пакет — **фиксированный снимок** всех его заявок, находившихся в буфере в этот момент. Новые заявки того же источника в него не попадают. **Пока все заявки пакета не завершились/не были выбиты, новый пакет не формируется**. |
| ОР1 | Итоговая таблица статистики источников и приборов выводится и без автоматического режима. |
| ОД3 | Для текущего шага печатается состояние всех объектов. По разъяснению преподавателя временные диаграммы и графики выводить не нужно. |

Приоритет задан как **И1 > И2 > И3** (меньший номер источника — выше приоритет). Все численные интервалы, число источников/приборов и размер буфера — **учебные настройки**, а не фиксированные параметры варианта.

## 2. Как запустить на Windows (PowerShell / VS Code)

Нужен **JDK 17+**, рекомендуем JDK 21. В папке `src`:

```powershell
javac -encoding UTF-8 App.java Model.java Dispatchers.java Statistics.java SimulationEngine.java ConsoleView.java SelfTest.java
java App
```

Или из корня данного каталога просто `./run.cmd` (в PowerShell ` .\run.cmd `).

**Управление:** Enter — один шаг; `c` — включить/скрыть календарь будущих событий; `a` — без остановок выполнить остальные шаги; `q` — закончить демонстрацию с промежуточной таблицей. При `--output` каждое состояние будет также сохранено в TXT. Можно не нажимать Enter, а сразу запустить `--batch` для создания полной истории.

Для демонстрации переполнения, пакетов и указателя:

```powershell
java App --workers 2 --buffer 3 --requests 25 --service-mean 5 --seed 42 --output ..\trace.txt
```

Автоматический просмотр **того же пошагового следа**, полезен для создания TXT, но это не отдельный автоматический режим курсовой:

```powershell
java App --workers 2 --buffer 3 --requests 25 --service-mean 5 --seed 42 --batch --output ..\trace.txt
```

Если нужен календарь (письменная памятка требует его, устное уточнение говорит обратное):

```powershell
java App --requests 10 --calendar --output ..\calendar_trace.txt
```

Настройка источников (для И1 [2,3], И2 [3,5], И3 [4,6]):

```powershell
java App --sources 2:3,3:5,4:6 --workers 2 --buffer 5 --requests 15 --service-mean 4 --seed 7
```

`--seed` позволяет показать преподавателю одни и те же шаги на каждом запуске. Без `--output` текст выводится только в терминале.

Если русские буквы на Windows отображаются неправильно, перед запуском в PowerShell можно выполнить `chcp 65001`, затем перезапустить команду.

## 3. Что считается шагом

Подход **особых событий**, рекомендованный пособием: модельное время перескакивает к ближайшей генерации или завершению обслуживания. По требованию преподавателя связанные действия показываются **отдельными микрошагами в тот же момент времени**:

1. `REQUEST_GENERATED`: источник создал заявку — диспетчер постановки получил триггер.
2. `BUFFER_EVICTED`: если буфер заполнен, оттуда удалена заявка по Д1ОО2, зарегистрирован отказ.
3. `BUFFER_ADDED`: новая заявка встала в конец БП по Д1ОЗ2.
4. `PACKET_CREATED`: на свободном приборе и при отсутствии активного пакета диспетчер выбора создаёт неподвижный состав пакета Д2Б5.
5. `REQUEST_SELECTED`: заявка берётся из пакета и удаляется из буфера.
6. `SENT_TO_WORKER`: по Д2П2 найден свободный прибор, назначено экспоненциальное время ПЗ1, создано событие окончания обслуживания.
7. `SERVICE_COMPLETED`: прибор освободился, статистика обновлена; только при полном завершении активного пакета можно создать новый.

Для *первой* заявки с изначально свободными приборами пусковым событием выбора выступает поступление заявки в буфер; далее стандартный триггер — **освобождение прибора**. Так система не зависает в пустом начальном состоянии; это также отражено в предоставленном `happy-flow.puml`.

**Почему время одного шага может не увеличиться?** Потому что постановка, выбор, поиск прибора и передача — мгновенные действия в одном моменте времени. Это детализация внешнего события, а не имитация дополнительных секунд. Календарь хранит будущие внешние события; немедленные микродействия находятся в очереди внутри движка.

## 4. Что показывается после каждого шага

- Номер шага, модельное время, тип события и пояснение;
- И1/И2/И3: число сгенерированных, границы равномерного закона, следующее время генерации;
- Буфер: **каждое место** с номером и заявкой либо прочерком;
- Фиксированный пакет: источник, исходный состав, ожидающие заявки, число ещё не завершённых;
- Приборы: свободен/занят, заявку и момент освобождения;
- Указатель Д2П2, после назначения — его новое положение;
- Отказы, завершённые и сгенерированные заявки, вероятность отказа (общая и по источникам), средние времена и дисперсии по источникам, текущие коэффициенты использования приборов;
- По запросу `c` — **таблица календаря** будущих генераций и завершений обслуживания.

## 5. Итоговая статистика (сводная ОР1)

Для каждого источника:

- `Nген` — число сгенерированных заявок;
- `Nотк` — число получивших отказ заявок (включая выбитые);
- `Nобсл` — число успешно обслуженных;
- `Pотк = Nотк/Nген`;
- `Tож` — среднее время ожидания в буфере (от генерации до начала обслуживания);
- `Tобсл` — среднее время обслуживания;
- `Tсист = Tож + Tобсл` — время пребывания в системе;
- `Dож`, `Dобсл` — выборочные дисперсии времени ожидания и обслуживания.

Средние времена считаются по **успешно завершённым** заявкам. Пока их нет, средние отображаются нулями (означает **недостаточно данных**, а не нулевую задержку).

Для каждого прибора: число обслуженных, суммарное время занятости и `Kисп = Tзанято / Tреализации`. При текущем состоянии занятость рассчитывается и для работающего сейчас прибора.

В конце `создано = обслужено + отказано`. После последней генерации **обслуживание продолжается** до опустошения буфера и окончания всех пакетов — требование методички.

`rho = Σλ / Σμ` (где `λᵢ = 2/(aᵢ+bᵢ)`, `μ = 1/Tmean`) — теоретическая оценка предлагаемой нагрузки. Она может не совпадать с фактической загрузкой из-за ограничений пакетной дисциплины и отказов.

## 6. Что соответствует твоим UML

Изначальные файлы лежат в `docs/` без изменений. Дополнительно:

- `docs/class-java-console.puml` — дополненная диаграмма классов текущего Java-кода: ссылка на Буфер у `PlacementDispatcher`, `Packet` с незавершёнными запросами, движение кольцевого указателя;
- `docs/sequence-java-console.puml` — последовательность по фактическим методам, с пунктирными ответами, зависимостью постановки и выбора, триггерами и закрытием **только после завершения** пакета.

**Примечание о расхождении UML:** в исходном `package-processing.puml` пакет закрывается по исчерпанию **списка ожидающих**, что не соответствует новому указанию преподавателя, если заявка всё ещё обрабатывается прибором. В Java-коде и новых UML пакет закрывается лишь когда нет ни одной **незавершённой** заявки в составе пакета.

Классы хранят приватное состояние: `SimulationEngine`, `Source`, `Request`, `Buffer`, `PlacementDispatcher`, `SelectionDispatcher`, `Packet`, `DevicePool`, `Worker`, `EventCalendar`, `Statistics`. `ConsoleView` отвечает исключительно за вывод, поэтому алгоритмы не перепутаны с UI.

## 7. Бизнес-домен и что будет потом

В качестве **примерного реального бизнес-домена** можно взять сервис фоновой обработки документов. Источники И1, И2, И3 — клиентские приложения с разным уровнем обслуживания, заявки — задания по обработке файла, приборы — вычислительные воркеры. Общая очередь хранит задания, обработка по клиентским пакетам уменьшает необходимость постоянного переключения между клиентскими контекстами. Равномерность поступления и экспоненциальность обработки здесь **предположения модели** — их ещё нужно обосновать для реальных данных.

По методичке третий этап — синтез конкретной **вычислительной** системы с выбранными входными параметрами и целевыми выходными характеристиками. Для полного третьего этапа помимо этого пошагового прототипа потребуются **автоматический режим**, настройка конфигураций и экономическое обоснование. Четвёртый этап методички посвящён окончательному выбору оптимальной конфигурации. Здесь реализована **только заказанная пошаговая часть**.

**Зонный буфер:** пригоден, когда надо гарантировать квоты памяти отдельным источникам или исключить вытеснение чужих заявок, но свободные зоны могут простаивать. Общий буфер использует всё доступное место гибче и выбран для базового проекта (допустимо в условиях преподавателя). Отдельной реализации зонного буфера здесь нет.
